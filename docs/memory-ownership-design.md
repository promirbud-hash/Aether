# Memory and ownership model — proposed baseline

**Status:** accepted baseline; implementation and language guarantees are
incomplete. The user approved value semantics, frame/tape regions, acyclic ARC
with optional COW, and the decisions recorded below. This document distinguishes
accepted semantics from the portions currently implemented.

## Design goals

- Observable value semantics without a garbage collector.
- Deterministic release for resources owned by a function or returned value.
- No observable mutation through aliases created by assignment or argument
  passing.
- Bounded temporary lifetimes for ordinary calls and autodiff.
- Acyclic ownership for the initial supported value types.
- No ownership rules inferred from raw C pointers or undocumented FFI behavior.

## Proposed semantic contract

### Values, bindings, and aliasing

1. Aether expressions produce values. Copying a value into another binding or
   passing it to a function has value semantics: later rebinding or mutation
   of one binding cannot change the value observed through another binding.
2. `let` and `const` bindings are immutable. `var` is mutable only by
   rebinding its identifier to a new value; it never enables mutation through
   an alias or pointer. Assignment to parameters and immutable bindings is
   rejected.
3. Aggregate values and tensor elements are not mutable through references in
   this baseline. Any future in-place update must operate through an explicit
   mutable binding and preserve value semantics by detaching shared storage.
4. The initial model has no user-visible references, slices, views, closures
   that capture owned values, or owning pointer fields. Those features need
   separate lifetime and aliasing contracts before they can be added.
5. These are observable semantics, not a requirement to physically copy every
   value. The implementation may use moves, immutable sharing, or
   copy-on-write (COW) if results remain indistinguishable from independent
   values.

### Parameters, returns, and ownership transfer

- A parameter is an independent language value for the duration of a call.
  The compiler may borrow immutable storage for that call, but the callee
  cannot retain a borrow beyond its invocation or mutate the caller's value.
- Returning an aggregate produces a value owned by the caller. A result must
  not refer to storage whose lifetime ends with the callee's frame.
- An implementation may transfer a unique allocation to the caller, retain
  shared immutable storage, or promote/copy frame-local data before return.
  The choice is not observable.
- Assignment/copy and return do not expose reference counts or allow programs
  to depend on whether a physical copy occurred.

### Frames and temporary regions

- Every function invocation has a logical frame region for its locals and
  non-escaping temporaries. Nested calls create nested regions.
- Frame-managed storage is released on every normal return and every
  recoverable `Result` exit, including a return generated by postfix `?`.
  Cleanup order is reverse construction order (LIFO) for resources whose
  destruction can observe other live resources.
- A value that escapes its frame must be moved to caller-owned storage or
  promoted to storage whose lifetime covers the caller. A frame-region
  address may never escape.
- Scalars and small fixed-size values may be represented inline. Larger
  aggregates and tensor buffers must use checked storage rather than relying
  on unbounded C stack use. Representation thresholds are implementation
  details and may not change language behavior.
- Recursive call depth and region growth require explicit limits or checked
  allocation behavior. Static shape information alone is not evidence that a
  stack allocation is safe.

### Autodiff tape region

- A `gradient` invocation owns a temporary tape region nested within its
  invocation frame. Forward intermediates and adjoints remain valid through
  the reverse pass and are released when the gradient operation completes.
- The returned gradient is an ordinary caller-owned value and cannot alias
  tape storage.
- Tape size calculations must check multiplication/addition overflow before
  allocation. Allocation failure must be surfaced according to the runtime
  failure policy; it must never produce a plausible but invalid gradient.
- The current bounded v0 implementation is consistent with this lifetime
  contract: interpreter-local lists and a checked, freed C99 tape allocation.
  It does not implement general frames or the general ownership rules here.

### Heap ownership and acyclic ARC

- Heap-backed values use deterministic automatic reference counting (ARC).
  Each live owning binding contributes one ownership reference; creating a
  second independent value may retain immutable backing storage, and the last
  release destroys that storage.
- For the bounded `FrameBuffer` ARC increment, every live owning local
  binding owns exactly one reference, while a function parameter is borrowed
  for the duration of the call. A fresh allocation starts at refcount 1;
  retaining checks for counter overflow and traps fail-fast. Each owned local
  releases once in reverse construction order on normal return and `?`; the
  backing allocation is freed once when the count reaches zero.
- Copy initialization retains before the new binding becomes live. Rebinding
  evaluates the right-hand expression first, retains it when it is borrowed,
  then releases the old binding and installs the new owner. This order makes
  `x = x` and expressions that read `x` safe.
- An internal function call borrows its resource arguments; it never releases
  a caller's reference. A returned resource is always owned by the caller.
  Returning a borrowed parameter or copying it into a local retains it;
  returning a local retains (or transfers) one reference before frame cleanup.
  Expression temporaries own their returned references and release them at
  the end of the containing full expression unless ownership is transferred
  to a binding, result, or caller.
- The compiler/runtime may transfer ownership instead of retaining when it
  proves the source is no longer used. This is an optimization of the same
  value semantics, not a user-visible move operation in the initial language.
- The initial ownership graph is acyclic by construction: aggregates contain
  values, not owning references to other independently mutable aggregates;
  shared immutable backing storage forms a DAG. Recursive by-value type
  layouts and any feature that can create owning back-references are rejected
  until a sound rule is specified.
- ARC operations and destruction must be inserted on all normal and
  recoverable exits. A reference count is an implementation mechanism, not a
  proof of safe aliasing or a substitute for the value/escape rules above.
- Cyclic references, weak references, finalizers, and user-defined
  destructors are outside this baseline.

### COW and mutation

- COW is permitted only as an optimization for immutable shared backing
  storage. A write through an explicitly mutable value must first establish
  unique storage; if storage is shared, it detaches before the write.
- No stale alias may observe the write. If uniqueness cannot be established or
  detachment fails, the operation must fail explicitly; it must not write
  through shared storage.
- COW does not change binding mutability, lifetimes, or the ownership graph.
  It is not required for the first implementation and may be omitted in favor
  of eager copying.

### Errors, cleanup, and allocation failure

- `Result<T, E>` and postfix `?` are recoverable control flow. Every owned
  resource in the exiting scope is released before the `Err` value is
  returned/propagated.
- The initial runtime has no exception unwinding contract. A process-aborting
  trap may terminate without running destructors; this is explicitly distinct
  from a recoverable `Result` exit.
- Size overflow is detected before allocation. Explicit allocation APIs, if
  introduced, should return a typed error. Compiler-generated allocations
  whose enclosing API has no allocation-error channel use the runtime's
  documented fail-fast trap policy, as the current C99 autodiff tape does.
- Allocation failure, failed COW detachment, and invalid ownership state may
  not be converted into a success-shaped value or silently ignored.

### FFI and external resources

- The current scalar C ABI subset carries no Aether-managed aggregate or
  tensor ownership across the boundary. Supported scalar FFI values use the C
  ABI's by-value representation and are not ARC-managed.
- Any future ownership-bearing value crossing into or out of C requires an
  explicit ownership-transfer contract at that boundary. Raw C ABI values do
  not receive implicit ARC retain/release behavior. Ownership-bearing
  aggregates, pointers, callbacks that capture values, and runtime-managed
  handles remain rejected until their transfer annotations and destruction
  rules are specified.
- The FFI contract must state transfer direction, nullability, error
  reporting, and which side destroys each resource. Generational handles may
  be considered for runtime-managed resources, but they do not replace C ABI
  pointer rules.
- GPU buffers are also deferred; their device, stream, and synchronization
  lifetimes must be specified independently.

## Decisions and boundaries

| Concern | Proposed baseline | Not claimed today |
|---|---|---|
| Language behavior | Value semantics; no observable alias mutation | General heap ownership enforcement |
| `let` / `const` / `var` | Immutable `let`/`const`; `var` rebinding only; assignment to immutable names rejected | In-place tensor or aggregate mutation |
| Temporary lifetime | Autodiff tape is per-call; one restricted frame-local byte buffer is cleaned on return and `?` | General frame allocator and arbitrary resource cleanup |
| Heap lifetime | Deterministic acyclic ARC for future heap-backed values | ARC implementation or cycle diagnostics |
| Cycles | Initial ownership graph is a DAG; owning back-references rejected | Cyclic GC, weak references, finalizers |
| COW | Optional, semantics-preserving optimization | Required COW behavior or mutability implementation |
| Recoverable failure | `Result` propagation cleans up | Exception unwinding |
| Trap | Fail-fast; cleanup is not promised after process abort | Recovery after trap |
| FFI/GPU | Separate future contracts required | Aggregate/tensor FFI or GPU ownership |

## Implementation gates

1. **Approve/finalize semantics:** **Accepted.** `var` is rebinding-only;
   implicit compiler allocation failure is fail-fast; `?` cleans up the
   current frame before propagating `Err`; ownership-bearing C crossings
   require explicit transfer and raw FFI values receive no automatic ARC.
2. **Type and escape analysis:** Initial rebinding checks and the bounded
   `FrameBuffer` boundary are implemented: locals, borrowed parameters, owned
   returns, and `Result` payloads are permitted, while resource-bearing
   aggregates and FFI crossings remain rejected. General ownership
   capabilities, arbitrary frame escapes, and recursive-layout analysis
   remain outstanding.
3. **Runtime representation:** private `FrameBuffer` storage uses checked
   positive byte sizes, immutable shared backing, and checked reference counts.
   General heap-backed scalar, aggregate, and tensor storage remains
   outstanding.
4. **Ownership lowering:** typed IR records retain, release, transfer, and
   temporary ownership operations for `FrameBuffer`. The interpreter and C99
   backend release frame bindings in LIFO order on normal returns and `?`;
   native tests verify exact counts through allocator hooks. ARC for arbitrary
   types remains outstanding.
5. **COW or eager copy:** COW is optional; current C99 fixed tensors are copied
   by value. Heap-backed COW or eager-copy behavior remains outstanding.
6. **Conformance:** frontend, semantic, interpreter, and C99 tests cover `var`
   rebinding, inline scalar `Result`, frame-buffer copy/parameter/return
   ownership, temporary cleanup, exactly-once LIFO cleanup on normal return
   and both `?` paths, nested calls, count/size overflow, and allocation
   failure. Still required are general heap copy isolation, ownership for
   arbitrary values, arbitrary destructors, and tensor gradient lifetime
   integration.
7. **Separate extensions:** design FFI ownership, cycles/handles, concurrency,
   and GPU-buffer lifetime before implementing those features.

The baseline is accepted, but milestone 13 remains only partially implemented.
Do not claim a general memory-safety or ownership guarantee until the remaining
gates and conformance tests pass.
